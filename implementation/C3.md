## 1. Overview

C3 mengirim transaksi offline ke backend via **`POST /api/v1/sync`** (RabbitMQ
async) dan merekonsiliasi status final via **`GET /api/v1/transactions`** (poll).
Backend adalah **source of truth**; frontend menyesuaikan ke kontrak, bukan
sebaliknya.

Status backend (terverifikasi): `/sync` & `/transactions` **SUDAH IMPLEMENTED**
— C3 tidak lagi menunggu D5. Status final transaksi **tidak** dikembalikan
langsung oleh `/sync` (respons hanya `{accepted, queued_at}`); frontend harus
poll `GET /transactions` lalu mencocokkan `offline_uuid`.

## 2. Kontrak Backend (wajib)

### POST /api/v1/sync
- Headers: `Authorization: Bearer <token>` (wajib), `Content-Type: application/json`. **Tidak ada** header `X-Device-ID`.
- Body (persis):
  ```json
  {
    "transactions": [{
      "offline_uuid": "<UUID v4>",
      "id_device": "<string>",
      "created_at_local": "<ISO8601>",
      "subtotal": <number>,
      "total": <number>,
      "notes": "<string|null>",
      "items": [{ "id_product": "<string>", "quantity": <int>=1,
                 "unit_price": <number>, "subtotal": <number> }],
      "payment": { "method": "CASH|STATIC_QRIS|BANK_TRANSFER", "amount": <number>,
                   "cash_received": <number|null>, "change_amount": <number|null>,
                   "qris_code": <string|null>, "transfer_ref": <string|null> }
    }]
  }
  ```
- Validasi: `offline_uuid` **wajib `@IsUUID(4)`**; money dikirim **number**;
  `forbidNonWhitelisted` → nama field harus PERSIS (else 400); **tidak ada**
  `payment_method` top-level (method ada di `payment.method`).
- Idempotensi: unik `[id_device, offline_uuid]`; HTTP selalu **200** (tidak ada
  409). `500` = broker RMQ down (pesan `"Message broker is currently
  unavailable"`) → retryable.
- Respons 200 (nested, setelah `TransformInterceptor`):
  `data: { message, data: { accepted:number, queued_at:ISO } }`. **Tidak ada**
  status per-transaksi.

### GET /api/v1/transactions
- Headers: `Authorization: Bearer <token>`.
- Query: `id_device`, `sync_status` (enum `PENDING_SYNC|SYNCING|SYNCED|SYNC_FAILED|SYNC_CONFLICT`),
  `cursor`, `limit` (cursor pagination).
- Respons (nested): `data: { data: [{ offline_uuid, sync_status, ... }], meta: { next_cursor, limit } }`.
  Money di response = **string** (`parseFloat` bila perlu).

## 3. Prasyarat & Blocker

| ID | Status | Dampak C3 |
|---|---|---|
| A2 (prefix `/api/v1`) | ⛔ belum di-merge (milik teman) | `requestJson` harus pakai `/api/v1/...` |
| A3 (unwrap `body.data`) | ⛔ belum di-merge (milik teman) | `requestJson` harus unwrap envelope `{status,message,data}` |
| D2 (`merchantId` decode JWT) | ⏳ wewenang teman (B2) | **Tidak dipakai** di payload C3 (cukup `session.token` + `device.id`) |
| D3 (`stock`) | ✅ fallback `0` | tak relevan C3 |
| D5 (`POST /sync`) | ✅ SUDAH IMPLEMENTED | C3 lanjut tanpa nunggu |
| D6 (money asimetris) | ✅ diketahui | kirim number, `parseFloat` baca response |

> C3 mengasumsikan A2/A3 sudah di-merge (sesuai keputusan "Tunggu A2/A3 merge").
> Sebelum itu, kode benar secara tipe tapi belum bisa di-run.

## 4. Scope & Blast Radius

## 5. Desain per Sub-task

### C3.4 — Model status (`models.ts`, `database.ts`, `initialize.ts`, `transaction-builder.ts`, `transaction-repository.ts`)
- `SyncStatus = "PENDING_SYNC" | "SYNCING" | "SYNCED" | "SYNC_FAILED" | "SYNC_CONFLICT"` (hapus `LOCAL_ONLY`, `FAILED`, `SettlementStatus`).
- `LocalTransaction.offlineUuid: string` (UUID v4 via `crypto.randomUUID()` di `buildLocalTransaction`).
- `transaction-builder.ts`: `syncStatus:"PENDING_SYNC"`, hapus `settlementStatus`.
- `transaction-repository.ts`: gate void pakai `syncStatus ∈ {SYNCED, SYNC_CONFLICT}` (pengganti `settlementStatus==="SETTLED"`).
- `initialize.ts` & `database.ts`: `LOCAL_ONLY`→`PENDING_SYNC`; hapus `settlementStatus` dari index.

### C3.1 — Transport (`api-client.ts`)
- `transactionPayload(transaction, deviceId)` → bentuk body per §2 (lihat §6).
  Buang `discount/tax/paymentVerificationType/operatorName/invoiceNumber/merchantId`.
- `sendTransactionBatch(session, device, _batchId, transactions)` → `POST /api/v1/sync`,
  body `{ transactions: transactions.map(t => transactionPayload(t, device.id)) }`,
  return `BackendSyncAck { accepted, queuedAt }`.
- Hapus import `syncResponseSchema`/`SyncResult` dari `@operator/contracts` (pertahankan `healthResponseSchema`).

### C3.2 — Unwrap & map respons
- Schema `backendSyncAckSchema = z.object({ message, data: { accepted, queued_at } })`.
  `sendTransactionBatch` kembalikan `{ accepted, queuedAt: data.queued_at }`.
  **Tidak** tandai `SYNCED` di sini (status final dari poll C3.8).

### C3.3 — Status policy (`sync-policy.ts`, `local-sync-repository.ts`, `sync-service.ts`)
- Hapus `transitionForResult` + `ResultTransition.settlementStatus` + import `SyncResult`.
- `applyResults` → **`applyAck(batch, ack, startedAt)`**: catat `SyncAttempt`
  (`result:"ACCEPTED"`), set `syncStatus:"SYNCING"`, `receivedAtBackend: ack.queuedAt`,
  outbox tetap `"SYNCING"` (agar tak di-resend; idempoten via `offline_uuid`).
- `SyncTransport` return type → `Promise<BackendSyncAck>` (bukan `SyncResult[]`).
- `sync-service.process`: sukses → `applyAck`; gagal → `applyTransportFailure` (retry saat network/5xx).

### C3.6 — Retry idempoten
- `requestJson` (milik teman) sudah set `retryable` untuk ≥500/network →
  `applyTransportFailure` retry otomatis. Backend selalu 200; resend aman karena
  idempotensi `[id_device, offline_uuid]`. Tidak ada perubahan besar.

### C3.8 — Rekonsiliasi (`transaction-api.ts` + `reconcile.ts`, build mandiri)
- `fetchTransactions(token, { id_device, sync_status, cursor, limit })` →
  `GET /api/v1/transactions`, parse `data:[{ offline_uuid, sync_status }], meta:{ next_cursor, limit }`.
- `reconcileSyncStatuses(session, device)`: ambil transaksi lokal
  `syncStatus ∈ {PENDING_SYNC, SYNCING}`, paginasi `GET /transactions?id_device=…&
  sync_status=SYNCED,SYNC_FAILED,SYNC_CONFLICT`, cocokkan `offline_uuid` →
  update lokal: `SYNCED` (hapus outbox), `SYNC_FAILED`/`SYNC_CONFLICT`
  (`syncStatus` + outbox `FAILED` untuk retry/resolve manual).
- **Hook** ke `browser-scheduler` via `sync-runtime.ts`: setelah `syncService.run()`
  tiap siklus, panggil `reconcileSyncStatuses` (best-effort, swallow error).
- **Keputusan**: build mandiri (tidak reuse fitur `reconciliation` milik teman/C6)
  untuk menghindari duplikasi & bentrok merge.

### C3.5 — UI (`status-badge.tsx` + konsumer)
- `SyncBadge` mendukung 5 status (`PENDING_SYNC, SYNCING, SYNCED, SYNC_FAILED, SYNC_CONFLICT`).
- **Hapus `SettlementBadge`** + import `SettlementStatus`. Konsumer diperbaiki:
  ganti badge settlement dengan pengecekan `syncStatus` (lihat §8).

### C3.7 — Test
- `lib/sync-engine.test.ts`: ganti test `transitionForResult` dengan coverage
  `transactionPayload` (UUID v4, nested `payment.method`, money number,
  `TRANSFER→BANK_TRANSFER`, field terbuang) + `mapProduct` (C1).
- `transaction-builder.test.ts` & `lib/checkout-service.test.ts`: perbarui
  `LOCAL_ONLY`→`PENDING_SYNC`, hapus `settlementStatus`, tambah `offlineUuid`.

## 6. Tabel Mapping (LocalTransaction → backend payload)

| Local | Backend | Catatan |
|---|---|---|
| `offlineUuid` | `offline_uuid` | **wajib UUID v4** |
| `deviceId` (param) | `id_device` | |
| `createdAt` | `created_at_local` | ISO |
| `subtotal` / `total` | `subtotal` / `total` | **number** |
| — | `notes` | `null` (tak ada sumber lokal) |
| `items[].productId` | `items[].id_product` | |
| `items[].quantity`/`unitPrice`/`subtotal` | `items[].quantity`/`unit_price`/`subtotal` | |
| `paymentMethod` | `payment.method` | `TRANSFER`→`BANK_TRANSFER` |
| `total` | `payment.amount` | |
| `amountReceived` | `payment.cash_received` | `null` jika undefined |
| `change` | `payment.change_amount` | `null` jika undefined |
| `paymentReference` | `payment.qris_code`/`transfer_ref` | by method |
| (dibuang) | — | `discount, tax, paymentVerificationType, operatorName, invoiceNumber, merchantId` |

## 7. Asumsi & Keputusan

1. `payment.amount` = `transaction.total` (jumlah transaksi).
2. `qris_code`/`transfer_ref` diisi dari `paymentReference` berdasarkan method.
3. Cegah resend berlebih: outbox status `"SYNCING"` pasca-ack (bukan `PENDING`)
   → tak dipilih lagi oleh `loadDueBatch`.
4. **`SettlementStatus` dihapus penuh** + seluruh konsumer diperbaiki (catatan ini).
5. **C3.8 build mandiri** (tidak reuse `reconciliation` teman).
6. `notes` selalu `null` (frontend belum punya field notes transaksi).

## 10. Risiko / Open Questions

- **A2/A3 belum merge** → C3 tak bisa di-run end-to-end sampai milik teman di-merge.
- **`PaymentMethod` lokal `TRANSFER` vs backend `BANK_TRANSFER`** → sudah di-handle mapping di `transactionPayload`; perlu konfirmasi backend tak menambah enum lain.
- **Bentrok merge dengan UI `transactions` milik teman** (karena penghapusan `SettlementStatus`) — koordinasi saat rebase.
- **`SYNC_CONFLICT`** butuh UI resolve manual (milik C6 teman); C3 hanya menandai status.
